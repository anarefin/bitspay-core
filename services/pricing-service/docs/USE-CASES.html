pricing-service — Use Cases, Features and Workflows

Who this is for: developers, QA and business analysts new to Bits Pay who need to understand what pricing-service does. No prior knowledge of MFS pricing is assumed.

Based on: SPEC.md (SVC-06 v6), pricing-algorithm.v1.md, pricing-golden-vectors.v1.json and openapi.yaml. If this guide and those files disagree, the spec and contracts win.

Status: the code is still the WP-0 skeleton. This guide describes the intended behaviour. Tags: R1 = first release, R2 = later release. ⚑ marks a provisional value that Finance or Marketing still has to confirm.

#1. The service in one minute

Every time money moves in Bits Pay, someone has to decide "what does this cost, and who earns what from it?". pricing-service owns all of those rules. It has two modules in one Spring Boot app:

💸 Fees

Fee per transaction (fixed, percent or slab), min/max, VAT, free monthly allowance, and who pays (payer, payee or operator). The merchant fee (MDR) is also a fee.

🤝 Commission

What the agent earns per transaction, the share passed up to distributors, monthly bonuses, clawbacks, and periodic payout (settlement) with tax (AIT) withheld.

🎁 Campaigns R2

Promotions such as cashback, bonus, referral, lucky draw, points and educational messages, with budgets, abuse checks and clawback.

✅ Maker-checker

Every rule change is proposed by one person and approved by a different person before it takes effect.

The most important design idea

The payment hot path never calls pricing-service. Instead:

  1. pricing-service publishes every active fee plan on a Kafka topic called fee.rules.
  2. transaction-service keeps a copy of those plans in memory and computes the fee itself, using the same algorithm (pricing-algorithm v1).
  3. Both services prove they compute identical numbers by passing the same golden vectors, a shared file of test cases.

Later, pricing-service reads the completed transactions from txn.events to record commissions and evaluate campaigns. This happens after the payment has completed.

Things it must NEVER do

  1. Use double/float for money, or round with anything other than HALF_EVEN.
  2. Debit a partner (agent/distributor) wallet. Clawbacks are netted against future payouts instead.
  3. Publish a plan that has not been approved by a checker other than its maker, or publish a future version before its start time.
  4. Store customer names, clear NID, full phone numbers or device ids. These are stored as HMAC hashes only.
  5. Call services other than ledger, wallet, limits-risk and admin.

The one rounding function: bpsOf

All percentage math in the service goes through one function. It computes base × bps / 10000 using integers only, and rounds half to even (banker's rounding). An exact .5 rounds to the nearest even number. Anything above .5 rounds up, and anything below rounds down.

static long bpsOf(long base, int bps) {          // base ≥ 0
  long n = Math.multiplyExact(base, (long) bps);
  long q = n / 10_000, r = n % 10_000;
  if (r > 5_000 || (r == 5_000 && (q & 1) == 1)) q++;
  return q;
}

#4. Use case 1 — Configure a fee plan R1

Who: a PRICING_MAKER proposes the plan and a PRICING_CHECKER approves it.

Why: fees change through configuration, never through a code deployment (SRS FEE-001, FEE-005, ADM-004).

Story. Bits Pay decides that from 1 November a cash-out costs 1.5 % plus 15 % VAT, and the agent earns 40 % of the fee. The maker types this in as plan PLN-CASHOUT-STD. The checker reviews it and approves it. At midnight on 1 November the plan goes live by itself.

Anatomy of a plan

PartWhat it saysOptions
txnTypeWhich transaction kind the plan pricesP2P, CASH_IN, CASH_OUT, MERCHANT_PAYMENT, MERCHANT_REFUND, FLOAT_TRANSFER, REVERSAL
matchOptional filters. null means "any".channel, payerWalletType, payeeWalletType, payerKycTier, categoryCode
priorityHigher wins when several plans match0..100000
effectiveFrom / effectiveToWhen the plan is valid. From is inclusive, To is exclusive, and a null To means open-ended.timestamps
feeHow the fee is computed, with a min/max clamp (maxPoisha = 0 means no cap)FIXED, PERCENT, SLAB, NONE
feeBearerWho paysPAYER, PAYEE, OPERATOR (SHARED reserved)
vatBpsVAT on the feee.g. 1500 = 15 %
freeMonthlyCountFirst N transactions per month are freee.g. 5
commissionWhat the agent earns, with its own min/max clamp and AITNONE, FIXED, PERCENT_OF_AMOUNT, PERCENT_OF_FEE

Workflow

  1. Create. The maker calls POST /v1/pricing/plans, which creates the plan and its DRAFT v1. Later changes go through POST …/{planId}/versions (new draft) and PUT …/versions/{v} (edit, using If-Match).
  2. Optional dry run. POST /v1/pricing/plans:validate checks the plan and returns sample quotes, without saving anything.
  3. Submit. POST …/versions/{v}:submit runs the validation rules and the golden self-check (every golden vector must still pass). The version becomes PENDING_APPROVAL and an approval request is created.
  4. Approve. A checker (≠ maker) calls POST /v1/approvals/{id}:approve. The golden self-check runs again.
  5. Go live. If effectiveFrom is in the future, the version becomes SCHEDULED, and the activation scheduler (every 10 s) switches it to ACTIVE at that moment. If effectiveFrom is now, it becomes ACTIVE immediately. Backdating more than 5 minutes is refused.
  6. Publish. In one DB transaction the old version becomes SUPERSEDED, the new one ACTIVE, and an outbox row is written. Debezium then sends PRICING_PLAN_UPSERTED to fee.rules.

  ACTIVE --> RETIRED : retire approved (tombstone)
  EXPIRED --> RETIRED : retire approved

Validation rules that catch beginners

  • SLAB: slabs must start at 1, be contiguous (next.from = prev.to + 1), and only the last slab may have toPoisha = null.
  • NONE fee ⇒ minPoisha = maxPoisha = 0. Also, feeBearer = OPERATOR ⇒ fee type must be NONE.
  • feeBearer = SHARED and commission.vatBps are rejected with RESERVED_VALUE, because those decisions are still open.
  • Commission beneficiary must be the agent side: CASH_IN → PAYER, CASH_OUT → PAYEE.
  • Regulatory caps ⚑: the fee at the sample amounts 100 Tk to 25 lakh Tk must stay within the configured caps (e.g. CASH_OUT ≤ 185 bps, P2P ≤ 25 Tk).
  • A retired planId can never be reused.

Retiring a plan

POST /v1/pricing/plans/{planId}:retire with a reason creates a RETIRE approval. Once it is approved, every version becomes RETIRED or WITHDRAWN, and a tombstone (key = planId, value = null) is published on fee.rules so that consumers delete the plan.

Spec ref: §3.4 F1/F2, §3.5, §5.1.4, BR-PRC-04..09, BR-PRC-20..27.

#5. Use case 2 — Quote a fee (the pricing algorithm) R1

Who: any service or staff tool, through POST /v1/pricing/quote. transaction-service runs the same algorithm in its own process.

Why: to show the fee before confirmation (SRS FEE-004) and to answer back-office "what if" questions. The response takes p99 ≤ 20 ms and is served from memory, without touching the DB.

Story. Karim wants to cash out 500 Tk at Salma's shop. The app asks "what will this cost?". The answer is a 7.50 Tk fee plus 1.12 Tk VAT, so Karim pays 508.62 Tk in total. Salma earns 3.00 Tk commission, of which 0.30 Tk is withheld as tax.

The 8 steps, in plain words

flowchart TD
  A["Step 0: resolve category
(agent/merchant side)"] --> B["Step 1: find candidate plans
ACTIVE, same txnType, in date range, match fields equal"]
  B --> C{"any candidate?"}
  C -- "no" --> Z["Return zero result
(planId null, all amounts 0)"]
  C -- "yes" --> D["Step 2: pick one
priority, then specificity, then version, then planId"]
  D --> E{"Step 3: free allowance left?"}
  E -- "yes" --> F0["fee = 0 (no min clamp)"]
  E -- "no" --> F["Step 4: fee by type
then clamp to min / max"]
  F0 --> G["Step 5: VAT = bpsOf(fee, vatBps)"]
  F --> G
  G --> H["Step 6: commission gross, clamp, AIT"]
  H --> I{"Step 7: bearer = OPERATOR?"}
  I -- "yes" --> J["fee = 0, VAT = 0"]
  I -- "no" --> K["Step 8: return 9 fields"]
  J --> K
  1. Step 0: category. If the payee is an agent, distributor, merchant or institution (A/D/M/I), use the payee's category; otherwise use the payer's. So CASH_OUT → the agent, MERCHANT_PAYMENT → the merchant, CASH_IN → the agent (who is the payer), and P2P → 0.
  2. Step 1: candidates. Keep plans that are ACTIVE, of the same txnType, with effectiveFrom ≤ at < effectiveTo, and whose every non-null match field equals the request.
  3. Step 2: selection. Highest priority wins. On a tie, the plan with more non-null match fields (more specific) wins, then the higher version, then the smaller planId.
  4. Step 3: free allowance. If the sender has used fewer than freeMonthlyCount transactions of this type this month, the fee is 0.
  5. Step 4: fee. FIXED → fixedPoisha. PERCENT → bpsOf(amount, percentBps). SLAB → find the slab containing the amount, then slab.fixed + bpsOf(amount, slab.percent). NONE → 0. Then clamp: max(fee, min), then min(fee, max) if max > 0.
  6. Step 5: VAT = bpsOf(fee, vatBps).
  7. Step 6: commission. Compute the gross by type, clamp it to the commission min/max, then compute AIT = bpsOf(gross, aitBps).
  8. Step 7: operator-borne. If the bearer is OPERATOR, the output fee and VAT are forced to 0.

#6. Use case 3 — Plans reach transaction-service R1

Who: transaction-service, a consumer of fee.rules.

Why: payments compute their fee locally and never wait on pricing-service. This only works if every copy of the plans and of the algorithm is identical.

How the copy stays in sync

  1. Bootstrap: on start-up, transaction-service pages through GET /v1/pricing/plans?status=ACTIVE (200 per page, following nextCursor until null). The header X-Snapshot-Outbox-Position tells it which point of the outbox the snapshot covers.
  2. Stream: it then consumes fee.rules. This is a compacted topic, so Kafka keeps only the latest value per planId. A newer value replaces the plan, and a null value (tombstone) deletes it. Values with status: "EXPIRED" are dropped.
  3. Prove: it downloads GET /v1/pricing/golden-vectors (whose ETag is a SHA-256 of the file) and must pass every CATALOGUE vector in its tests.
  4. Heal: if the topic is ever damaged, an admin calls POST /v1/internal/pricing/fee-rules:republish (with Idempotency-Key), which re-writes every current value and tombstone.
sequenceDiagram
  participant P as pricing-service
  participant O as outbox table
  participant D as Debezium
  participant K as fee.rules (compacted)
  participant T as transaction-service
  T->>P: GET /v1/pricing/plans?status=ACTIVE (paged)
  P-->>T: items[] + X-Snapshot-Outbox-Position
  T->>P: GET /v1/pricing/golden-vectors
  P-->>T: vector file + ETag

Timing note: a version is published when it becomes ACTIVE, not when it is approved. Publishing it early would overwrite the plan that is still current. The switch may lag by up to 30 s, which is alerted (OPEN D-44).

Spec ref: §5.1.2, §5.1.3, §5.2.1, ADR-03, ADR-04, BR-PRC-09a/b.

#7. Use case 4 — In-line agent commission R1

Who: agents such as Salma. Commission is defined in the same pricing plan as the fee.

Why: agents are paid for each cash-in and cash-out they serve (SRS COM-001, COM-003).

"In-line" means that the agent's commission is paid inside the payment itself: transaction-service posts it in the payment's ledger chain. pricing-service only records it afterwards, as a statement line.

How the record is made

  1. transaction-service publishes TRANSACTION_COMPLETED on txn.events, carrying commissionPoisha, aitPoisha and the beneficiary wallet.
  2. The pricing consumer first filters out irrelevant events without writing to the DB, which keeps 5k TPS cheap.
  3. For a relevant event it writes an INLINE accrual at level 0 with status INLINE_SETTLED. The money has already moved, so it is never paid again. It also emits COMMISSION_ACCRUED.
  4. If the beneficiary is missing, it is derived from the txnType (CASH_IN → sender, CASH_OUT → receiver). Otherwise the event is parked.

Spec ref: BR-PRC-16, BR-PRC-24/25, BR-PRC-28/29, vectors G2, G3, X8, X9.

#8. Use case 5 — Hierarchical commission sharing R2

Who: the distributors above an agent (sub-distributor, distributor, master).

Why: the whole distribution chain is rewarded for each agent transaction (SRS COM-002).

Story. Salma reports to Rupa Telecom, which reports to Dhaka North, which reports to Bengal Master. When Karim cashes out at Salma's shop, all three distributors earn a small share from a separate pool that the operator funds.

The share rule

{ "ruleId": "CSR-CASHOUT-STD", "txnType": "CASH_OUT", "matchAgentSubType": null,
  "poolBasis": "FEE", "poolBps": 2000, "unassignedMode": "RETAIN_OPERATOR", "priority": 100,
  "splits": [ {"ancestorRole": "DISTRIBUTOR:SUB",         "shareBps": 5000, "aitBps": 1000},
              {"ancestorRole": "DISTRIBUTOR:DISTRIBUTOR", "shareBps": 3000, "aitBps": 1000},
              {"ancestorRole": "DISTRIBUTOR:MASTER",      "shareBps": 2000, "aitBps": 1000} ],
  "effectiveFrom": "2026-11-01T00:00:00.000Z", "effectiveTo": null }

In plain words: pool = 20 % of the fee. Half of the pool goes to the sub-distributor, 30 % to the distributor and 20 % to the master. The splits must add up to 10000 bps. Share rules go through the same draft → submit → approve lifecycle as plans (/v1/commissions/share-rules), but they are not published to Kafka.

When a level is missing

  • RETAIN_OPERATOR: the 30 % share (45) is simply not paid, and the operator keeps it.
  • NEAREST_PRESENT_ANCESTOR: the 30 % is added to the nearest ancestor that is present.

The hierarchy is effective-dated. A cash-out completed on 31 Oct but processed later still uses the old chain.

#10. Use case 7 — Reversal & commission clawback R1

Who: triggered automatically by TRANSACTION_REVERSED events.

Why: if a transaction is undone, the commission earned on it must be undone too (SRS COM-006), but a partner wallet is never debited.

What happens

  1. A reversal arrives with reverseCommission = true.
  2. For every INLINE and SHARE accrual of that transaction, a negative CLAWBACK accrual is added, with the same beneficiary and level and minus the gross and AIT.
    • INLINE clawback → INLINE_SETTLED, because the ledger reversal already returned the in-line money.
    • SHARE clawback → ACCRUED, and it is netted in the next settlement.
  3. If reverseCommission = false (e.g. a partial or fee-only reversal), nothing is clawed back by default.
  4. If the reversal arrives before the completion event (out of order), it waits in pending_clawback. When the completion arrives, the commission is accrued and immediately clawed back.

Example: Rupa's share is clawed back after it was paid

EventGrossAITStatus
Week 1: share from Karim's cash-out758SETTLED (paid)
Week 2: Karim's cash-out reversed → CLAWBACK−75−8ACCRUED
Week 2: new shares earned606ACCRUED
Week 2 settlement net−15−2net = −13 ≤ 0 → SKIPPED, carried forward

Finance is alerted (COMMISSION_NEGATIVE_BALANCE) when a carried negative exceeds 1,000 Tk ⚑ or is older than 90 days. Recovery is done by a treasury manual journal, not by this service.

Spec ref: §7.7 BR-PRC-40..45, ADR-08. The week-2 numbers are illustrative.

#11. Use case 8 — Commission settlement (payout) R1

Who: the settlement job (daily at 03:10 Dhaka time, after end of day), plus FIN_MAKER and FIN_CHECKER.

Why: accrued commission (shares, bonuses, adjustments) is paid to the partner's wallet on a schedule, with AIT withheld (SRS COM-004/005).

Settlement profiles

PartnerDefault frequency ⚑Mode
AgentWEEKLY (period starts Saturday)WALLET
Distributor (all subtypes)MONTHLYWALLET
Merchant / institutionno profile (they earn no commission)—

A FIN_MAKER can change a profile (PUT /v1/commissions/settlement-profiles/{walletId}, which needs approval) or hold payouts immediately (:hold). Releasing a hold (:unhold) needs approval. mode = BANK is not supported yet and returns 422.

Workflow

  1. For each partner whose period has ended: sum every ACCRUED accrual with business date ≤ period end, including carried-forward ones. Then net = Σ gross − Σ AIT.
  2. Decide the outcome:
    • net ≤ 0 or below minPayoutPoisha → SKIPPED (the accruals carry forward)
    • profile on hold or partner not ACTIVE → HELD
    • gross ≥ 1 lakh Tk ⚑ → PENDING_APPROVAL (FIN_CHECKER; two levels at ≥ 10 lakh Tk)
    • otherwise → POSTING
  3. The settlementId (also used as the ledger commandId) and a txnRef such as CMS-20261007-K3M9QX2A are saved before the ledger call.
  4. Call ledger post-commission-settlement. The gross comes from COMMISSION_PAYABLE, the AIT goes to AIT_PAYABLE and the net goes to the partner's wallet.
  5. Handle the result:
    • OK or EXISTS → SETTLED, and COMMISSION_SETTLED is emitted.
    • Timeout or 503 → retry later with the same commandId, so the payout is never doubled.
    • REJECTED → FAILED, and the profile is put on hold. :retry re-plans the payout with a new id.
stateDiagram-v2

  PLANNED --> SKIPPED : net <= 0 or below min payout
  PLANNED --> HELD : on hold or partner not ACTIVE
  PLANNED --> PENDING_APPROVAL : gross over threshold
  PLANNED --> POSTING : below threshold
  PENDING_APPROVAL --> POSTING : approved
  PENDING_APPROVAL --> CANCELLED : rejected / expired
  POSTING --> POSTING : timeout or 503 (same commandId)
  POSTING --> SETTLED : ledger OK / EXISTS

#12. Use case 9 — Adjustments & disputes R1

Who: FIN_MAKER (raises), FIN_CHECKER (approves), and partners or OPS_MAKER (open disputes).

Why: real life has mistakes, such as missed accruals or wrong rules, and they need a controlled way to fix them (SRS COM-006).

Manual adjustment

Salma reports that she was not credited for a cash-out. Finance confirms it and raises a +120 Tk adjustment.

POST /v1/commissions/adjustments (Idempotency-Key required)

{ "beneficiaryWalletId": "0192f4a1-0a01-7c00-8a00-00000000a001",
  "grossPoisha": 12000, "aitBps": 1000,
  "reasonCode": "MISSED_ACCRUAL", "reference": "Ticket 0192f9aa",
  "relatedTxnRef": "CO26100300Q8XK2M1D" }

AIT = sign × bpsOf(|12000|, 1000) = 1200. The adjustment needs one approval below 1 lakh Tk ⚑ and two at or above it. Once approved, it becomes an ADJUSTMENT accrual (level 8, ACCRUED) that is paid in the next settlement. A negative grossPoisha reduces what the partner is owed.

Dispute

  1. The partner (or ops) opens POST /v1/commissions/disputes, listing the accrual ids and a description. Those accruals become DISPUTED and are excluded from settlement.
  2. FIN_MAKER resolves it with POST …/disputes/{id}:resolve and outcome UPHELD or REJECTED. UPHELD with an amount creates an adjustment, which needs approval.
  3. Either way, the disputed accruals return to ACCRUED and are paid normally.

Spec ref: BR-PRC-62, BR-PRC-63, §5.1.8.

#13. Use case 10 — Maker-checker approvals R1

Who: every staff role, from both modules, through one approval engine.

Why: no single person can change money rules alone (SRS BOM-004/005).

Engine rules

  • The checker must not be the maker. A second-level checker must differ from the first-level one.
  • Approvals expire after 72 h, and the entity then returns to its previous state (e.g. a plan version becomes REJECTED and a campaign goes back to DRAFT).

  • Every transition publishes approval.events and audit.events.

#15. Use case 12 — Referrals, lucky draws, points, education R2

Referral

Karim shares his code KRM7Q2X with Rahim. Rahim signs up and claims the code within 7 days. When Rahim's KYC is approved, both of them get a reward.

  1. Karim calls GET /v1/referrals/codes/{walletId}. The code is deterministic (an HMAC of the wallet id), so it is always the same for the same wallet.
  2. Rahim calls POST /v1/referrals/claims with { "refereeWalletId": "…", "referralCode": "KRM7Q2X" }. The claim becomes PENDING_QUALIFICATION. A code entered at registration also creates the claim.
  3. Qualification happens on KYC_APPROVED or on Rahim's first qualifying transaction. Two rewards are created (REFERRER and REFEREE), each with its own budget check.
  4. Guards: no self-referral, different NIDs, at most 20 rewarded referrals per referrer ⚑, and the claim must be within the claim window.

Lucky draw (provably fair)

  1. Qualifying transactions earn draw entries (entriesPerTxn).
  2. The maker requests a draw with a seed commitment, i.e. the SHA-256 of a secret seed (POST …/draws). This needs approval.
  3. After approval the maker reveals the seed (…:reveal). The service verifies it against the commitment and ranks entries by HMAC-SHA256(seed, entryId). Nobody can pick the winners, and anyone can reproduce the result.
  4. Each wallet can win at most once. Prizes become WINNER rewards, paid from the campaign budget.

Points and educational campaigns

  • POINTS: a non-monetary counter (GET /v1/wallets/{walletId}/points). It is off by default (points.enabled = false) and cannot be redeemed yet.
  • EDUCATIONAL: no money involved. At sendAt the segment is snapshotted and messages are queued on notification.requests, throttled to 200 per second.

Spec ref: §3.4 F7, BR-CMP-48/49, BR-CMP-54/55, ADR-19, §5.1.13–5.1.14.

All jobs use ShedLock, so only one replica runs each job. There is no Redis. The caches are in-memory Caffeine:

  • PlanSnapshot: rebuilt after every plan change and every 60 s. It serves quotes, and a quote returns 503 if the snapshot is older than 5 min while the DB is down.
  • ActiveCampaignIndex: maps txnType to active campaigns, refreshed on change and every 30 s.
  • Refdata cache: FEATURE.CAMPAIGN and CUTOFF.EOD.

#20. Where it will live in code

A layered Spring Boot app. Port 8106, management port 9106, DB schema svc_pricing.

PackageHolds
com.bracits.bitspay.pricing.pricingPlans, evaluator (PricingEvaluator, Rounding.bpsOf), validator, accruals, sharing, settlement, incentives, adjustments. Tables are unprefixed.
com.bracits.bitspay.pricing.campaignCampaigns, segments, triggers, rewards, budgets, clawback, referrals, draws. Tables are prefixed campaign_.
com.bracits.bitspay.pricing.commonMaker-checker engine, outbox, idempotency, ShedLock, HMAC hasher, refdata cache

Each module has the layers controller, dto, service, repository, entity, mapper, exception, client, messaging and config. The modules never call each other directly. Only the public facades (PricingFacade, CampaignFacade) may be used, and ArchUnit enforces this. The campaign module can be switched off entirely with bitspay.modules.campaign.enabled=false, which is how R1 goes live.
