#1. The service in one minute

For every payment in Bits Pay, limits-risk-service (SVC-05) answers one question within 50 ms (p95):

"May this money move? If so, reserve the usage."

It does three jobs:

Job Plain words
Limits engine "Rahim may send at most 50,000 Tk per day by P2P." It keeps per-wallet counters (day / week / month) and reserves usage atomically so two parallel payments can never both squeeze past the limit.
Fraud engine "A new phone plus a large amount to a stranger looks suspicious." Rules are data (a JSON DSL), not Java code. Each matching rule adds a score, and the score maps to a decision.
Lists Blacklist and whitelist of wallets, devices, phone numbers, NIDs, bank accounts, IPs and partners. Values are stored as hashes, never in clear text.

All configuration (limits, rules, lists, emergency switches) is changed through maker-checker: one person proposes and a different person approves.

#Things it must NEVER do (memorise these)

  1. Call any other service synchronously, touch the ledger or TigerBeetle, or read another service's DB schema.
  2. Return ALLOW without a successful reservation. If Redis is down it returns 503; it never guesses.
  3. Change a limit counter anywhere other than the three Lua scripts (limit_reserve.lua, limit_release.lua, limit_reapply.lua).
  4. Release a reservation twice, or release one whose transaction completed.
  5. Store or log a clear NID, bank account number or full phone number.
  6. Hard-code a fraud rule in Java.
  7. Apply any config, rule, list or emergency change without maker-checker and an audit event in the same DB transaction. The only exceptions are the EMERGENCY_SINGLE path and a customer lowering their own self-limit.

#3. Use case 1 — Evaluate a payment (the hot path)

Endpoint: POST /v1/risk/evaluate · Caller: transaction-service only · Budget: p95 ≤ 50 ms (limits part ≤ 10 ms)

#3.1 The story

Rahim (customer, KYC Tier 2) sends 500 Tk to Karim (customer, Tier 1) from the app.

  1. transaction-service calls evaluate with txnId, txnType = P2P, amountPoisha = 50000, and both party snapshots.
  2. limits-risk checks, in memory: emergency controls, the wallet/device blacklist, and per-transaction min/max.
  3. In one atomic Redis Lua call it checks and increments Rahim's send counters and Karim's receive counters for day, week and month. In parallel it reads and updates the fraud aggregates.
  4. It scores the fraud rules (score 12, below every threshold) and returns ALLOW with reservationId = txnId.
  5. Later the ledger posts the payment and TRANSACTION_COMPLETED arrives, so the reservation is committed. If the ledger refuses, TRANSACTION_FAILED arrives and the counters are released.
sequenceDiagram
  participant T as transaction-service
  participant R as limits-risk api
  participant RC as Redis critical
  participant RA as Redis aggregate
  T->>R: POST /v1/risk/evaluate
  R->>R: emergency controls, blacklist (wallet, device), per-txn min/max, resolve limits (memory)
  par limits
    R->>RC: EVALSHA limit_reserve.lua (FROM D/W/M + TO D/W/M)
    RC-->>R: OK, usageBefore = 7
  and fraud aggregates
    R->>RA: agg_touch(from), agg_touch(to), device set
    RA-->>R: aggregates, profiles, device facts, beneficiary flag
  end
  R->>R: blacklist MSISDN/NID/PARTNER from profiles, rules, score 12, combine
  R-->>T: 200 ALLOW, reservationId = txnId
  Note over R: ALLOW writes nothing to Postgres (metrics only)

  "amountPoisha": 50000,

Things to notice:

  • txnId is a UUIDv7. It equals the reservation id and the ledger commandId, and it is never re-used.
  • The service trusts the party snapshot (walletType, kycTier, flags) from the caller, so it never has to call wallet-service on the hot path.
  • flags is a bitmask: 1 AML_WATCH, 2 PIN_RESET_COOLING, 4 PRE_REGISTERED, 8 HAS_OPEN_LIEN, 16 NEW_DEVICE_COOLING.
  • at is the transaction creation time. If it is more than 5 minutes off server time, server time is used.
  • context (IP, geo, SIM, failed auth) is null in R1 because the edge layer does not exist yet.

#3.3 Response: ALLOW

{ "decision": "ALLOW", "reasonCodes": [], "riskScore": 12, "reservationId": "0192f3c1-7a2b-7c00-9a51-3f2c8e1d0a11",
  "receiverMaxBalancePoisha": 10000000, "usage": { "senderMonthlyCountForTxnType": 7 }, "violatedLimit": null }
  • receiverMaxBalancePoisha = 10000000 is Karim's Tier 1 max balance (100,000 Tk). This service does not enforce max balance. The caller passes the value to the ledger, which enforces it atomically.
  • usage.senderMonthlyCountForTxnType = 7 means Rahim made 7 P2P sends this month before this one. pricing-service uses it for "first N free" allowances.
  • Every decision returns HTTP 200. The caller maps decisions to its own 422 errors.

#3.4 The seven decisions and their precedence

When several things go wrong at once, the strongest decision wins:

SERVICE_DISABLED  >  BLOCK  >  LIMIT_EXCEEDED  >  HOLD  >  STEP_UP  >  ALLOW_AND_ALERT  >  ALLOW
   (emergency)   (blacklist     (a limit)        (fraud score / rule action)     (alert,     (clean)
                  or rule)                                                     still pays)
Decision Money moves? Reservation kept? Alert on risk.alerts? Saved in risk_decision?
ALLOW yes yes no no (metrics only)
ALLOW_AND_ALERT yes yes yes yes
STEP_UP no (terminal decline in R1) released yes yes
HOLD no (terminal decline in R1) released yes yes
LIMIT_EXCEEDED no never made / released only if alertOnLimitExceeded yes
BLOCK no released / never made yes yes
SERVICE_DISABLED no never made no yes

reasonCodes uses this vocabulary: LIMIT:<limitCode>, BLACKLIST:<type>:<FROM|TO>, EMERGENCY:<controlCode>, <ruleId> (e.g. FR-BEN-001), and STEP_UP_UNSUPPORTED_CHANNEL.

#3.5 Worked examples, one per decision

#A. LIMIT_EXCEEDED: Karim's daily receive limit

Seed: Tier 1 customer, P2P RECEIVE daily amount = 50,000 Tk = 5,000,000 poisha.

poisha Tk
Karim already received today (incl. outstanding reservations) 4,980,000 49,800
This payment 50,000 500
Would become 5,030,000 50,300
Limit 5,000,000 50,000

5,030,000 > 5,000,000, so the payment is rejected. Remaining headroom = max(0, 5,000,000 − 4,980,000) = 20,000 poisha (200 Tk).

  "receiverMaxBalancePoisha": 10000000, "usage": { "senderMonthlyCountForTxnType": 7 },
  "violatedLimit": { "limitCode": "P2P_RECEIVE_DAILY_AMOUNT", "party": "TO", "walletId": "0192f2bb-0000-7000-8000-00000000b002",
    "scope": "P2P", "direction": "RECEIVE", "dimension": "DAILY_AMOUNT", "layer": "TIER",
    "limitValue": 5000000, "currentValue": 4980000, "attemptedValue": 50000, "remainingValue": 20000,
    "resetsAt": "2026-10-09T18:00:00.000Z" } }

resetsAt is Dhaka midnight (00:00 on 10 Oct in Dhaka = 18:00Z on 9 Oct).

The order of checks matters, because only the first violation is reported:

  • Party FROM before TO.
  • Then by dimension: DAILY_COUNT → DAILY_AMOUNT → WEEKLY_COUNT → WEEKLY_AMOUNT → MONTHLY_COUNT → MONTHLY_AMOUNT.
  • Then by scope: txnType → groups (alphabetical) → ALL.

#B. LIMIT_EXCEEDED: per-transaction checks (memory only, no Redis)

Rahim (Tier 2) tries to send 30,000 Tk by P2P. The Tier 2 P2P per-txn range is 10–25,000 Tk, so 3000000 > 2500000 and the result is P2P_SEND_PER_TXN_MAX. For these checks currentValue, remainingValue and resetsAt are null, and no reservation is attempted.

A Tier 0 customer tries any P2P send. Tier 0 P2P SEND has TXN_ALLOWED = 0, so the result is LIMIT_EXCEEDED with code P2P_SEND_TXN_ALLOWED, limitValue 0 and attemptedValue 1.

#C. HOLD: fraud score

Rahim sends 25,000 Tk to Karim from a phone first seen 2 hours ago, and he has never paid Karim before.

Rule Why it fires Weight
FR-NEWDEV-001 device first seen < 1440 min ago and amount ≥ 1,000,000 poisha 45
FR-BEN-001 first-time beneficiary and amount ≥ 1,000,000 poisha 30
Score 75

Thresholds: ALLOW_AND_ALERT ≥ 30, STEP_UP ≥ 50, HOLD ≥ 70, BLOCK ≥ 90. A score of 75 gives HOLD.

sequenceDiagram
  participant T as transaction-service
  participant R as limits-risk api
  participant RC as Redis critical
  participant PG as Postgres
  T->>R: POST /v1/risk/evaluate (25,000 Tk, new device, first-time beneficiary)
  R->>RC: limit_reserve.lua
  RC-->>R: OK (counters incremented)
  R->>R: FR-NEWDEV-001 (45) + FR-BEN-001 (30) = 75 >= HOLD 70
  R->>RC: limit_release.lua (FROM), limit_release.lua (TO), state X
  R->>PG: one txn: INSERT risk_decision + outbox RISK_ALERT_RAISED
  R-->>T: 200 HOLD, reasonCodes [FR-NEWDEV-001, FR-BEN-001], reservationId null

The counters were incremented by the Lua call, so the service compensates (releases) them synchronously before replying. A declined payment must never eat into anyone's limit.

#D. ALLOW_AND_ALERT: the payment goes through, but someone should look at it

Rahim has already made 5 sends in the last 10 minutes. FR-VEL-001 (agg.from.sendCount.10m ≥ 5, weight 30) fires, giving a score of 30, which is ≥ 30, so the decision is ALLOW_AND_ALERT. The reservation is kept, the payment proceeds, and a RISK_ALERT_RAISED is published.

#E. STEP_UP and its fallback

Rahim's PIN was just reset (flags & 2) and he sends ≥ 5,000 Tk, so FR-SIM-002 fires with action: STEP_UP. If the channel is APP, the decision is STEP_UP. If the channel is API or SYSTEM (they cannot do a step-up challenge), the decision falls back to HOLD and STEP_UP_UNSUPPORTED_CHANNEL is added. In R1 both STEP_UP and HOLD are terminal declines.

#F. BLOCK: blacklist

The sending device d-999 is on the blacklist. It is caught in memory before Redis, so nothing is reserved:

{"decision":"BLOCK","reasonCodes":["BLACKLIST:DEVICE:FROM"],"riskScore":100,"reservationId":null,
 "receiverMaxBalancePoisha":null,"usage":{"senderMonthlyCountForTxnType":null},"violatedLimit":null}

riskScore is set to maxScore (100). Note that usage is still an object; it is never null, though its field can be.

A rule can also BLOCK. FR-CICO-001 (agent and customer share the same MSISDN hash, i.e. agent self-dealing) has action: BLOCK.

#G. SERVICE_DISABLED: emergency freeze

Ops froze USSD cash-out for Tier 0 customers (control EC-000017). The response is "decision": "SERVICE_DISABLED", "reasonCodes": ["EMERGENCY:EC-000017"], with no Redis calls and no alert. See §8.

  participant T as transaction-service

The service never says ALLOW when it could not reserve. The caller treats 503 as "do not move money" and sends a release in case the reservation partly happened.

#3.6 The full algorithm (13 steps)

  1. Validate the body, headers and caller. A walletType: "S" gets 400 SYSTEM_PARTY_NOT_ALLOWED.
  2. Resolve for both parties, in memory: user category, risk grade, applicable limits, emergency controls.
  3. Freeze? If so, SERVICE_DISABLED. Stop.
  4. Blacklist from memory (WALLET of both parties, DEVICE). A hit gives BLOCK. Stop.
  5. Per-txn checks (TXN_ALLOWED, MIN, MAX). A failure marks LIMIT_EXCEEDED and skips the reservation; fraud still runs.
  6. In parallel: (a) limit_reserve.lua, (b) fraud aggregates, device set, geo.
  7. Blacklist from profiles (MSISDN, NID, PARTNER hashes of both parties).
  8. Fraud rules (skipped for bypassTxnTypes; whitelist suppression applies).
  9. Combine using precedence, then apply the STEP_UP fallback.
  10. Compensate: if something was reserved but the decision is not ALLOW / ALLOW_AND_ALERT, release it now.
  11. Persist non-ALLOW decisions to risk_decision (plus the alert) in one DB transaction. If Postgres is down, the decision is still returned and the write retries from an in-memory queue (10,000 entries, 5 min).
  12. Remember the first decision and score on the Redis index (async) so that a retry returns the same answer.
  13. Metrics: bitspay_risk_decisions_total{decision}.

#3.7 Idempotency: calling twice with the same txnId

  • Still reserved: the Lua script sees the records already exist and returns DUP plus the stored decision and score. The response repeats the same ALLOW / ALLOW_AND_ALERT, score and reservationId. Nothing is counted twice, and there is no second alert.
  • Already released or expired: the response is 409 STATE_CONFLICT, reason TXN_ID_RELEASED. A txnId is never re-used.

#4. Use case 2 — Reservation lifecycle

The evaluate call only reserves. What happens to that reservation afterwards is driven by events from transaction-service.

#4.1 State machine

stateDiagram-v2
  [*] --> RESERVED: evaluate ALLOW or ALLOW_AND_ALERT

  RESERVED --> COMMITTED: TRANSACTION_COMPLETED

  RESERVED --> EXPIRED: sweeper, age 10 min and watermark passed

  COMMITTED --> [*]: TTL
  RELEASED --> [*]: TTL
  EXPIRED --> [*]: TTL

Index codes in Redis (lri:<txnId> field s): R reserved, B batch held, C committed (final), X released, E expired.

#4.2 What actually sits in Redis

For the Rahim → Karim payment on 2026-10-09 (a Friday), with weeks starting on Saturday, the keys are:

Key Meaning
lc:{rahimWallet}:D:20261009 Rahim's day counters
lc:{rahimWallet}:W:20261003 Rahim's week counters (week began Sat 3 Oct)
lc:{rahimWallet}:M:202610 Rahim's month counters
same three for {karimWallet} Karim's counters
lr:{rahimWallet}:<txnId>, lr:{karimWallet}:<txnId> per-party reservation record (what was added, where), used to undo or redo exactly
lri:<txnId> index: from, to, state, created time, first decision, score
lrpend:<n> sorted set of reservations waiting for an outcome (used by the sweeper)

Inside each counter hash, fields look like <scope>:<dir>:c (count) and <scope>:<dir>:a (amount). dir is S (send), R (receive) or X (any), and * means "ALL". For Rahim's P2P send the service always increments P2P:S:c, P2P:S:a, *:S:c and *:S:a in all three period hashes. It also increments scope-group fields (and X "any" fields) when an active rule references them. Counters are maintained even when no rule exists, so a new rule works immediately.

#4.3 Worked counter example

Rahim's day hash, field P2P:S:a (amount) / P2P:S:c (count):

Step Event P2P:S:a P2P:S:c State
0 start of example 350,000 3 —
1 evaluate 500 Tk → ALLOW 400,000 4 R
2a TRANSACTION_COMPLETED (commit) 400,000 (kept) 4 C (record deleted)
2b or TRANSACTION_FAILED (release) 350,000 3 X (record kept, rel=1)
3 after 2b, a late TRANSACTION_COMPLETED arrives (re-apply) 400,000 4 C

Step 3 is not a bug. If money really moved, it must count against the limit, even if the reservation had been released in the meantime. Re-apply does no limit check; it records the truth.

#4.4 Commit, release and re-apply by event

sequenceDiagram
  participant K as txn.events
  participant W as limits-risk worker
  participant RC as Redis critical
  participant RA as Redis aggregate
  K->>W: TRANSACTION_FAILED (txnId, fromWalletId, toWalletId)
  W->>RC: limit_release(FROM), limit_release(TO), state X
  K->>W: TRANSACTION_COMPLETED (txnId, createdAt, completedAt)
  W->>RC: idx_state C (returns previous state)
  alt previous state R (normal)
    W->>RC: limit_reapply = plain commit, records deleted
  else previous state E or X (expired or released earlier)
    W->>RC: limit_reapply re-increments, no limit check
    W->>W: bitspay_limitsrisk_expired_then_completed_total +1
  end
  W->>RA: update sender profile + receiver last activity
  W->>RC: txnwm[partition] = watermark

Safety rules for releases:

  • They are idempotent: a second release does nothing.
  • A counter never goes below 0. If it would, it is clamped and bitspay_limitsrisk_counter_clamped_total is incremented; that metric must stay 0.
  • Duplicate deliveries of these two events need no inbox table. Each effect is naturally idempotent (release marks rel=1, commit deletes the record).

#4.5 Orphans: the guarded sweeper

What if transaction-service crashed and no event ever arrives? The sweeper (every 30 s, leader pod only) expires reservations older than 10 minutes, but only if the txn.events watermark has moved past created + 10 min on every partition.

Example: a reservation created at 08:03:22.

  • At 08:14 it is a candidate (older than 10 min).
  • If the Kafka consumer is lagging and the slowest partition watermark is 08:12:00, then 08:13:22 is not ≤ 08:12:00, so it is not expired. A COMPLETED event may still be in the queue.
  • Once all partitions pass 08:13:22, the reservation is released and its state becomes E.
sequenceDiagram
  participant S as Sweeper (leader)
  participant RC as Redis critical
  S->>RC: HGETALL txnwm
  S->>S: W = min over all partitions (missing partition means W = 0)
  loop n in 0..15
    S->>RC: ZRANGEBYSCORE lrpend:n -inf (now - 10 min) LIMIT 0 500
    S->>S: keep members with createdMs + 10 min <= W
    S->>RC: per txn: limit_release(FROM), limit_release(TO), state E
  end

Why so careful? If Kafka is down, wrongly expiring a reservation would "give back" headroom for money that actually moved. Stalling is the conservative choice: counters may stay high for a while, but they can never overshoot.

#4.6 The release API

Endpoint: POST /v1/limits/reservations/{txnId}:release Callers: transaction, disbursement and pricing services, SYSTEM, and staff (staff releases are audited).

{ "reasonCode": "ROW_FAILED" }

→

{ "txnId": "0192f4d0-0000-7000-8000-000000000001", "released": true, "state": "RELEASED" }

state is one of four final answers:

  • RELEASED: released now or earlier.
  • COMMITTED: the transaction completed, so nothing was released.
  • EXPIRED: the sweeper already released it.
  • NOT_FOUND: there was no reservation.

All of these return HTTP 200, so callers can retry safely from a persisted job.

#4.7 Optional: restore on reversal

Restore on reversal is off by default (restore-on-reversal = false). When it is on, TRANSACTION_REVERSED / TRANSACTION_REFUNDED give back the original's counters: the amount by the reversed or refunded delta, and the count by 1 only for a full reversal. Counters are clamped at 0 and never give back more than the original contributed.

Spec ref: §3.4 F3–F5, §3.5, §4.2, §5.1.3, §6.1, §7.2 (BR-05-17..22), §7.7

#5. Use case 3 — Usage / headroom

#7.1 Building blocks

  T --> R["Limit rules<br/>(scope × direction × dimension = value)"]

#7.2 Precedence: which number wins?

For each (scope, direction, dimension):

  1. Within a layer, the most specific row wins (most non-null of kycTier / riskGrade / channel).
  2. Across layers, for "upper" dimensions (max, counts, amounts):
base = min(tier, product/channel)          -- whichever is stricter
v    = override ?? base                     -- an override may raise OR lower …
v    = min(v, regulatory cap)               -- … but never beat the regulator
v    = REDUCE active ? floor(v × bps / 10000) : v
v    = SEND && self-limit ? min(v, self) : v
null = unlimited

For PER_TXN_MIN the maximum wins instead (the strictest minimum).

Behind the flag bitspay.features.self-limits.enabled (default false). A customer may set their own lower SEND caps for DAILY_AMOUNT, MONTHLY_AMOUNT or PER_TXN_MAX.

#8. Use case 6 — Emergency controls

When something is on fire (for example, a USSD cash-out fraud wave), ops can apply one of two kinds of control:

Kind Effect
FREEZE Matching payments get SERVICE_DISABLED, with no Redis and no alert
REDUCE Matching limits are multiplied by reduceBps / 10000 (5000 = halve). Does not apply to MAX_BALANCE or TXN_ALLOWED

A control matches when every non-null filter matches: txnType, channel, walletType, userCategory, kycTier, direction. Null means "any".

#Two approval modes

Mode Who What happens
MAKER_CHECKER RISK_ANALYST, OPS_MAKER PENDING_APPROVAL until a checker approves
EMERGENCY_SINGLE RISK_CHECKER, CAMLCO, ADMIN only ACTIVE immediately. A post-facto review approval is created, due in 24 h, and must be approved by another person. Rejecting it deactivates the control. If the review is overdue, the control stays effective as PENDING_REVIEW and a siem=true log line is written

#9.2 Hashing: why you cannot send a clear NID

Values are stored as HMAC-SHA256(BITSPAY_PLATFORM_HMAC_KEY, normalize(type, value)) in lower-case hex (kernel K2), plus a masked display form.

Type Normalisation Mask
MSISDN digits only; 01711000000 → 8801711000000 (13 digits) 8801711****00
NID digits only (10/13/17) ******1234
WALLET / PARTNER lower-case UUID first 4 + ****
BANK_ACCOUNT <bankCode>:<digits> first 4 + ****

Because MSISDN is normalised before hashing, 01711000000 and 8801711000000 produce the same hash, so both are caught.

For NID and BANK_ACCOUNT you must send valueHash. Sending a clear value gives 400 CLEAR_VALUE_NOT_ALLOWED, so a clear NID never appears in a URL or a log.

#10.3 Three-valued logic: missing data never fires a rule

A predicate over a missing attribute is UNKNOWN, not false.

Expression Result
all with any FALSE FALSE
all with no FALSE but an UNKNOWN UNKNOWN
any with any TRUE TRUE
not UNKNOWN UNKNOWN

A rule fires only on TRUE.

Example: FR-GEO-001 (ctx.geo.kmhSinceLast ≥ 500). In R1 context is null, so the attribute is missing, the predicate is UNKNOWN, and the rule never fires. That is why the GEO, AUTH and SIM-001 rules are seeded in SHADOW mode.

#10.4 Rolling aggregates

agg_touch.lua keeps per-wallet velocity buckets (1 min, 5 min, 1 h, 1 day resolution) in the aggregate Redis. It returns the "before" values, then increments them.

These count attempts, including later-declined ones, so a burst of tries is visible. Facts that should reflect completed activity (beneficiary set, average send amount, last activity) are updated from TRANSACTION_COMPLETED.

If the aggregate store is down, the setting fraud.on-aggregate-unavailable decides what happens:

  • REFUSE (seed): 503.
  • DEGRADE: evaluate with those attributes UNKNOWN.

#10.7 Rule versions and SHADOW mode

stateDiagram-v2
  [*] --> DRAFT
  DRAFT --> DRAFT: edit
  DRAFT --> PENDING_APPROVAL: submit with mode and effectiveFrom
  PENDING_APPROVAL --> REJECTED: rejected or expired
  PENDING_APPROVAL --> SCHEDULED: approved, effectiveFrom in future
  PENDING_APPROVAL --> ACTIVE: approved, mode ENFORCE
  PENDING_APPROVAL --> SHADOW: approved, mode SHADOW
  SCHEDULED --> ACTIVE: effectiveFrom reached
  SHADOW --> ACTIVE: promote (new approval)
  ACTIVE --> RETIRED: retire approved or superseded
  SHADOW --> RETIRED: retire approved or superseded

SHADOW means the rule is evaluated and its hits are counted (bitspay_limitsrisk_rule_hits_total{mode="SHADOW"}), but it never affects the decision or raises an alert. It is a safe way to measure a new rule on live traffic before enforcing it.

A typical workflow:

  1. POST /v1/risk/rules (with a definition or fromTemplate) creates DRAFT v1.
  2. POST /v1/risk/rules:validate compiles it and reports errors.
  3. PUT /v1/risk/rules/{ruleId}/versions/{v} edits the draft (with If-Match).
  4. POST /v1/risk/rules/{ruleId}/versions/{v}:submit with mode: SHADOW sends it to a RISK_CHECKER for approval.
  5. Watch the hit metrics for a week.
  6. POST /v1/risk/rules/{ruleId}/versions makes a new draft; submit it with mode: ENFORCE and get it approved.
  7. POST /v1/risk/rules/{ruleId}:retire retires the rule when it is no longer needed.

Reading:

  • GET /v1/risk/rules
  • GET /v1/risk/rules/{ruleId}/versions
  • GET /v1/risk/rules/{ruleId}/versions/{v}

#11. Use case 9 — Simulation and history 🕒 R2

Question it answers: "Before I enforce this rule, how often would it have fired over the last 90 days?"

  • A history writer (consumer group .history, flag bitspay.risk.history.enabled, default off) copies every txn.events record into txn_history (daily partitions, 90 days).
  • POST /v1/risk/simulations with 1..20 candidate rules and a window of ≤ 90 days → 202 { simulationId, status: QUEUED }.
  • The worker replays history through an in-memory aggregate store. It never touches Redis. ctx.* attributes and the blacklist are UNKNOWN during a replay.
  • GET /v1/risk/simulations/{id} returns, per rule:
    • hits and hit rate per 10k transactions;
    • the would-be decision distribution;
    • the amount affected;
    • overlap with live decisions;
    • the top 20 wallets and 100 sample txnIds.
  • Only one run per user at a time (409 SIMULATION_RUNNING).
  • A rule submission may reference its simulationId, so the checker can see the evidence.

Spec ref: §5.1.9, §6.2, §7.9, WP-9

#What "apply" means

The final approval does all of the following in one DB transaction:

  • applies the change;
  • bumps config_version;
  • writes history;

Pods then reload within 2 s. Audit payloads carry hashes and masks only.

#What happens when something breaks

Failure Behaviour
Redis critical down 503 for evaluate, batch, release, usage. Never ALLOW without a reservation
Aggregate Redis down REFUSE → 503 (seed), or DEGRADE → fraud attributes UNKNOWN
Postgres down ALLOW path unaffected (books in memory). Non-ALLOW decisions still returned and their writes retried. Config, list and approval APIs → 503
Kafka down / lag releases and commits are delayed; the watermark stalls, so nothing expires (conservative)
Config never loaded readiness DOWN, evaluate → 503

#Two Redis modes (ADR-01)

  • SINGLE_SLOT (default): one Lua call reserves both parties atomically.
  • PER_PARTY (Redis Cluster): one call per party. If one party rejects, the other is released immediately.

Overshoot is impossible in both modes. The test suite proves this: 200 threads × 500 Tk against a 50,000 Tk daily limit gives exactly 100 ALLOW and 100 LIMIT_EXCEEDED.
