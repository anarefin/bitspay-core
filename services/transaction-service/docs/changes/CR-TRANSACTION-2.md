> **Rejected 2026-10-14 (product owner).** Superseded by the MVP decision: there is **no PIN** in the MVP. Customers still transact over the REST API, identified by trusted `X-Actor-*` headers set by the authenticated channel / gateway (SRS A-43). The existing contract (1.1.0) already allows this, so nothing is applied and no consumer is re-pinned. Per-customer PIN, OTP and step-up stay R1.

## 1. Motivation
In the MVP release (SRS v1.2) there is no customer PIN set/change/reset and no OTP. Those are R1 (ONB-014 deferred, A-43). Even so, the MVP must let customers start payments through the REST API, and staff or agents must be able to start them on a customer's behalf.

The decision (MVP decisions, 2026-10-14): every money-moving customer operation carries a PIN. The PIN is the same fixed value for every MVP customer, **`1234`**, and is held in configuration. This exercises the R1 PIN contract from day one and gives a deliberate confirmation step, without building PIN management. Per-customer PINs replace it in R1 through a configuration switch, with no contract change.

## 2. Change (before → after)
**REST (`openapi.yaml`, info.version 1.1.0 → 2.0.0)**
- New header parameter `X-Actor-Pin` (string, pattern `^[0-9]{4}$`, never logged and never echoed).
- It is **required when `X-Actor-Type = CUSTOMER`** on the five money-moving operations: `POST /v1/payments/p2p`, `/v1/payments/cash-out`, `/v1/payments/merchant`, `/v1/payments/bill-payment` and `/v1/payments/recharge`.
- It is ignored for every other actor type and on quotes, enquiries, reads and beneficiaries.
- A missing or wrong PIN returns `403 ACTOR_NOT_ALLOWED` with the new reason `PIN_INVALID`. This is checked before idempotency and before any side effect, and `401` stays reserved for the edge layer (kernel).
- Staff- or agent-assisted customer payments send the customer's `X-Actor-*` headers plus the PIN. `X-Actor-User-Id` records the assisting staff user, and `X-Channel` records the channel (`BACKOFFICE` / `PARTNER_APP`).

```http
POST /v1/payments/p2p
X-Actor-Type: CUSTOMER
X-Actor-Wallet-Id: 0192f9b0-…-c1
X-Actor-Pin: 1234        # new; wrong / absent → 403 ACTOR_NOT_ALLOWED reason PIN_INVALID
```

**Codes (`codes.yaml`)**
- `problemReasons` gains `ACTOR_NOT_ALLOWED/PIN_INVALID`.
- `metrics` gains `bitspay_transaction_pin_rejected_total{operation}`.

**Behaviour (SPEC)**
- `ActorContextFilter` gains `PinVerifier` (service), with config `bitspay.auth.pin-mode`:
  - `MVP_FIXED` compares the PIN in constant time with the BCrypt hash `bitspay.auth.mvp-fixed-pin-hash`. The hash is of `1234`, and the raw value is never in config or logs.
  - `PER_CUSTOMER` is reserved for R1 and fails startup in the MVP build.
- The `prod` profile refuses to start with `MVP_FIXED`.
- No lock-out or retry counter in the MVP; a rejected PIN is counted in the metric and audited.
- Delegated P2P from disbursement-service (R1+, not deployed in the MVP) must send the PIN too. The analysis lists it as an impacted consumer.
