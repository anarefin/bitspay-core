Bits Pay MVP: use-case flows, end to end

This page traces each MVP use case from the first API call to the last booking. For every step it names the service, how the call is made (REST, Kafka, Redis or DB), the ledger command and legs, the events, the notifications and the GL accounts.

Built from bitspay-core service SPECs §3.4 (key flows), the CR log and the SRS v1.2 MVP release. The money examples reuse the SPEC personas (Rahim, Karim, Salma, Padma, Nirob Store). Amounts are in poisha (100 poisha = 1 Tk).

Call types: REST sync HTTP KAFKA async event REDIS cache / idempotency DB own Postgres IN-PROC inside the service

MVP scope and the services involved

The MVP has six customer-facing features and four supporting capabilities. Real off-us integrations (ekPay, aggregators, Bangla QR, telco APIs) come in R1, so bill payment and recharge use the in-process SimulatedBillerClient.

Shared payment pipeline (transaction-service)

Every money-moving payment (use cases 1–7, plus float transfer) runs the same fixed steps in this order. The per-feature sections below only call out where a feature differs.

  1. Validate and gate. Check the request schema, bind the actor (X-Actor-Wallet-Id must be the debited wallet, or the agent for agent operations), and check the product switch FEATURE.<PRODUCT> is on. IN-PROC
  2. Claim idempotency. Run EVAL idem_claim idem:{actorId}:{Idempotency-Key}. NEW continues. HIT with the same hash replays or re-drives. HIT with a different hash returns 409 IDEMPOTENCY_CONFLICT. REDIS critical
  3. Check wallet status. Pipelined HGET ws:{bucket} for both wallets. The value is version:status:tier:type:flags, written by wallet-service. Both wallets need status A, and the type pair must be allowed. REDIS cache
  4. Evaluate risk and reserve limits. POST /v1/risk/evaluate to limits-risk returns ALLOW, a reservation (id = txnId), receiverMaxBalancePoisha and usage. In the MVP, STEP_UP and HOLD are terminal declines. REST
  5. Price. Done locally from plans received on fee.rules (PRICING_PLAN_UPSERTED). Produces the fee, VAT, fee bearer, commission, AIT and commission source. IN-PROC
  6. Persist the intent. INSERT txn_intent with status INITIATED. DB
  7. Post to the ledger. POST /v1/ledger/commands/post-* with commandId = txnId. The ledger returns OK, EXISTS or REJECTED (final). REST
  8. Record the outcome. In one DB transaction: UPDATE status COMPLETED|FAILED WHERE status = INITIATED and an outbox row. Debezium then publishes it to txn.events. DB KAFKA

Headers (GLOBAL-CONVENTIONS K3)

  • X-Actor-Type: CUSTOMER, AGENT, MERCHANT, DISTRIBUTOR, INSTITUTION, STAFF, SYSTEM or SERVICE
  • X-Actor-Id, X-Actor-Wallet-Id, X-Actor-User-Id, X-Actor-Roles (staff)
  • X-Channel (APP, API, USSD…), X-Device-Id
  • Idempotency-Key is required on every money-moving POST

TX-MVP-AUTH: no PIN, OTP or step-up. The gateway or channel sets trusted X-Actor-* headers, and customers call the REST API directly (SRS A-43). CR-TRANSACTION-2 (fixed PIN) was rejected.

After the outcome commits

  • txn.events: TRANSACTION_COMPLETED, TRANSACTION_FAILED, TRANSACTION_REVERSED, TRANSACTION_REFUNDED
  • Consumers: limits-risk (counters, reservation commit), admin-service notification (rule engine → IN_APP + SMS), support, pricing
  • The ledger CDC publishes ledger.changes → general-ledger-service (books) and treasury (float positions, liquidity alerts)
  • Crash after the ledger post: the sweeper (every 5 s, intents older than 30 s) asks GET /v1/ledger/commands/{txnId} and completes or fails the intent

  • Pod crash after the post → the sweeper completes the intent (TX F8)

10. Support dispute and reversal (wrong transfer)

MVP supportingREVERSAL · prefix RVledger cmd 14 create-hold · cmd 7 post-reversal · code 1013support F2, F4 · TX F7

Actor and entry

  • SUP_MAKER opens POST /v1/support/disputes (txnRef, WRONG_TRANSFER, placeHold)
  • Records recipient consent, then calls :resolve UPHELD
  • SUP_CHECKER approves POST /v1/approvals/{id}:approve. Back-office reversals keep maker-checker; only onboarding is single-step
  • Reversible products: commands 1–6, 8, 12, 18, 19. BILL_PAY and RECHARGE are included (BR-S-38)

What the reversal does

  • Voids the support hold first (leg 0), then mirrors the original legs 0–4 with code 1013
  • No wallet-status gate, no risk call, no pricing, no max-balance constraint
  • The provider is not told about reversals of bill pay or recharge (TX-MVP-6)
